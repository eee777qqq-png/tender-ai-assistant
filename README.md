# tender-ai-assistant

Автоматизация подготовки к участию в госзакупках для СМСП (см.
[CLAUDE.md](CLAUDE.md) — полный контекст продукта и протокол контроля
качества). Пока реализовано два агента конвейера:

- **Агент 1 (Монитор ЕИС)** — клиент сервиса отдачи информации ЕИС
  (`zakupki.gov.ru`) по подтверждённому официальной инструкцией протоколу
  (см. [docs/eis-integration-instruction-2025.pdf](docs/eis-integration-instruction-2025.pdf)):
  забирает документы по региону заказчика за конкретную дату, сам
  отфильтровывает те, что относятся к разделу «Строительство», и копит их
  в локальном хранилище (`data/monitor.sqlite3`), не опрашивая повторно уже
  обработанные дни — рассчитан на регулярный запуск (cron/Планировщик
  заданий).
- **Агент 11 (Онбординг клиента)** — модель профиля клиента (4 блока полей
  + статусная модель) и проверка на полноту/достоверность перед тем, как
  профилем воспользуется Агент 6.
- **Метрика готовности к выборочному аудиту** (общая инфраструктура для
  агентов 3, 4, 6) — трекер, который решает, можно ли перевести агента с
  полной проверки эксперта на выборочный аудит, по правилам протокола
  контроля качества.
- **Лог расхождений** (часть ТЗ Агента 4) — структурированная запись, что
  именно эксперт поправил в выдаче агента, плюс статистика по самым частым
  расхождениям.
- **Агент 2 (Классификатор)** — справочник ОКПД2 по разделу «Строительство»
  (коды 41/42/43, 548 записей из официального классификатора) и проверка,
  относится ли код закупки к строительству. По решению владельца — весь
  раздел «Строительство» в скоупе, без сужения под нишу капремонта. Плюс
  сопоставление профиля клиента (Агент 11) с конкретной закупкой —
  регион, СРО, опыт, финансовая готовность — на тестовых данных
  (`classifier/sample_tenders.py`), пока Агент 1 не отдаёт полные
  структурированные закупки.
- **Агент 6 (Сборщик документов)** — пока каркас: проверяет, что профиль
  клиента в статусе `READY` (жёсткая ошибка, если нет), и строит заготовку
  пакета документов — какие поля нужны и из какого поля профиля/закупки
  каждое берётся. Содержательной генерации нет — зависит от Агента 3
  (не специфицирован).

## Доступ к ЕИС: что реально нужно (проверено по официальной инструкции)

Хорошая новость: отдельного соглашения с Федеральным казначейством
**не требуется**. Доступ оформляется самостоятельной регистрацией через
ЕСИА (Госуслуги) в личном кабинете ЕИС:

1. Зайти на [zakupki.gov.ru](https://zakupki.gov.ru/epz/main/public/home.html)
   → «Все разделы» → «Дополнительная информация» → «Открытые данные» →
   «Получение открытых данных».
2. Авторизоваться подтверждённой учётной записью руководителя организации
   в ЕСИА (для юрлица) или физлица (для ИП).
3. Зарегистрировать нового потребителя машиночитаемых данных, указать цель
   получения данных.
4. Для юрлица — загрузить сертификат руководителя/организации (им же
   потом устанавливается mTLS-соединение с сервисом, отдельный сертификат
   для транспорта не нужен). Для физлица/ИП — получить токен.

Подробности и скриншоты — в
[docs/eis-integration-instruction-2025.pdf](docs/eis-integration-instruction-2025.pdf)
(официальная «Инструкция по использованию сервисов отдачи информации ЕИС»,
2025 год, разделы 3–6).

**Что сервис умеет и чего не умеет:**
- Отбор документов только по региону заказчика + подсистеме + типу
  документа + **одной конкретной дате** за запрос (`exactDate`) — диапазон
  дат не поддерживается, для мониторинга нужно опрашивать сервис за каждый
  день.
- **Фильтра по ОКПД2 на стороне ЕИС нет.** Именно поэтому в проекте есть
  Агент 2 (`classifier.ConstructionClassifier`) — документы скачиваются
  целиком по региону, а на «стройку» отфильтровываются уже у нас.
- Открытый вопрос: точный `subsystemType`/`documentType44` для реестра
  *извещений* (закупки, которые ещё можно выиграть), а не уже заключённых
  контрактов — он приведён в «Альбоме ТФФ ЕИС» (раздел 2.9.19), который не
  входит в общедоступную инструкцию. Сейчас в конфиге стоят значения из
  примера в инструкции (`RGK`/`contract` — реестр контрактов), их нужно
  заменить на код реестра извещений, когда он будет уточнён.
- Если сертификат юрлица на ГОСТ-криптографии (частый случай), `requests`
  не сможет установить с ним TLS-соединение напрямую — используйте
  локальный туннель `stunnel-msspi` + КриптоПро CSP, точная инструкция по
  настройке для Windows Server и Linux — в Приложениях 3–4 того же PDF
  (сервис слушает `int44.zakupki.gov.ru:443`, а клиент стучится в
  `http://localhost:8080`, куда туннель прозрачно домаршрутизирует TLS).
- `*.zakupki.gov.ru` предъявляет сертификат, выпущенный российским
  национальным УЦ (Минцифры, `Russian Trusted Sub CA`) — его нет в
  стандартном наборе доверия `certifi`, из коробки TLS-проверка падает с
  `CERTIFICATE_VERIFY_FAILED`. Решено добавлением официального корня
  Минцифры к доверенным (`eis_client/tls.py` + `eis_client/ca_bundle/`),
  а не отключением проверки — подробности в докстринге модуля.
- **Проверено на реальном запросе (2026-09-17, токен физлица, регион 77):**
  TLS/сеть/токен в заголовке — всё доходит до сервиса (HTTP 200), но в
  ответе приходит буквальное эхо отправленного запроса вместо
  `getDocsByOrgRegionResponse` с `archiveUrl` — не SOAP-фолт, не сетевая
  ошибка. Не удалось объяснить вариацией `SOAPAction`, `User-Agent` или
  cookie-привязкой балансировщика (`priv-dstorebus-route`) — перепробовано,
  результат не меняется. Похоже на то, что доступ по токену ещё не
  полностью активирован на стороне ЕИС (самостоятельная регистрация могла
  создать «отложенный» доступ) — не подтверждено, стоит уточнить в
  поддержке ЕИС или проверить статус токена в личном кабинете.

## Установка

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows
# source .venv/bin/activate   # Linux/macOS
pip install -r requirements.txt
```

## Настройка

1. Скопируйте `.env.example` в `.env`:

   ```bash
   copy .env.example .env
   ```

2. Заполните в `.env` (полный справочник полей — в самом `.env.example`):
   - `EIS_CONSUMER_TYPE` — `legal_entity` или `individual_person`.
   - Для `legal_entity`: `EIS_CLIENT_CERT` / `EIS_CLIENT_KEY` (положите файлы
     в `certs/`, эта папка уже в `.gitignore`). Для `individual_person`:
     `EIS_INDIVIDUAL_PERSON_TOKEN`.
   - `EIS_ORG_REGION` — код региона (`77` = Москва).
   - `EIS_SUBSYSTEM_TYPE` / `EIS_DOCUMENT_TYPE44` — см. предупреждение выше
     про реестр контрактов vs реестр извещений.

## Запуск

```bash
python src/fetch_purchases.py --date 2026-09-15
python src/fetch_purchases.py --date 2026-09-15 --out docs.csv
```

Дата обязательна к смыслу (по умолчанию — вчера), потому что сервис не
поддерживает диапазон дат — только один `exactDate` за запрос.

При ошибке конфигурации или недоступности сервиса скрипт печатает понятную
причину (нет сертификата, сетевая ошибка, SOAP fault) и завершается с
кодом 1.

### Регулярный мониторинг (`run_monitor.py`)

`fetch_purchases.py` — для разовой проверки одной даты. Для постоянной
работы (Агент 1 и должен быть монитором, а не разовым скриптом) — `run_monitor.py`:

```bash
python src/run_monitor.py
python src/run_monitor.py --start-date 2026-09-01   # только при первом запуске на пустом хранилище
```

При каждом запуске он смотрит, какая дата последней обработана в
`data/monitor.sqlite3`, и опрашивает ЕИС по одному дню за все дни между ней
и вчера включительно (сегодняшний день ещё не завершён, ЕИС не отдаёт его
целиком). Если упадёт на середине — при следующем запуске продолжит с того
же дня, а не с самого начала. Найденные документы копятся в том же файле
(`MonitorStore.all_documents()` — прочитать всё найденное на сегодня).

Поставьте `run_monitor.py` в cron / Планировщик заданий Windows на
ежедневный запуск, чтобы Агент 1 работал без ручного участия.

## Профиль клиента (Агент 11)

Статусная модель — 4 стадии, переход на последние две делает человек, а не
автоматика:

```
DRAFT (черновик) → FILLED (заполнен) → EXPERT_REVIEWED (проверен экспертом) → READY (готов)
```

```python
from onboarding import ClientProfile, LegalInfo, validate_profile

profile = ClientProfile(client_id="client-1", region_code="77", legal=LegalInfo(inn="7701234567", ...))

issues = validate_profile(profile)  # DRAFT <-> FILLED, автоматическая проверка
if issues:
    for issue in issues:
        print(issue.block, issue.field, issue.message)  # профиль остаётся в DRAFT

# только человек может подтвердить или отклонить:
profile.submit_expert_review(reviewer="Edwin", approved=True, notes="проверил документы")
# approved=False вернул бы профиль обратно в DRAFT

profile.mark_ready()  # EXPERT_REVIEWED -> READY

if profile.is_ready_for_agent_6():
    ...  # только теперь можно передавать профиль Агенту 6
```

`validate_profile()` проверяет заполненность всех 4 блоков (юр.данные,
допуски/опыт, мощности, финансовая готовность) и базовую достоверность
форматов (ИНН, ОГРН, email, телефон) — она может перевести профиль только
между `DRAFT` и `FILLED`. `submit_expert_review()`/`mark_ready()` — ручные
шаги, вызвать их раньше времени (например, проверить черновик) —
`ValueError`. Согласно протоколу контроля качества, Агент 6 обязан
проверять `profile.is_ready_for_agent_6()` (== `READY`) перед
использованием данных клиента.

## Метрика готовности к выборочному аудиту (агенты 3, 4, 6)

```python
from quality_control import AuditReadinessRegistry

registry = AuditReadinessRegistry()
tracker = registry.get("agent_4_smetchik")

# после каждой проверки эксперта над выдачей агента:
tracker.record_check(needed_correction=False)  # или True, если эксперт правил

if tracker.requires_human_review():
    ...  # выдача обязательно идёт на проверку эксперта
else:
    ...  # агент в режиме выборочного аудита
```

Правила зашиты в `AuditReadinessTracker` по протоколу контроля качества:
скользящее окно последних 50 проверок, переход на выборочный аудит при
≥90% без существенной корректировки и 0 критических ошибок в окне; любая
критическая ошибка после перехода — немедленный откат на полную проверку
эксперта с историей в `tracker.rollback_history`.

## Классификатор ОКПД2 «Строительство» (Агент 2)

```python
from classifier import ConstructionClassifier

classifier = ConstructionClassifier()
classifier.is_construction_code("41.20.10.110")  # True
match = classifier.classify("43.99.90.280")
print(match.name)  # человекочитаемое название по справочнику

classifier.search("реставрации")  # все коды, где в названии есть это слово
```

Справочник (`data/okpd2_construction.csv`) — это весь официальный раздел
ОКПД2 «Строительство» (коды 41, 42, 43, все уровни, 548 записей). По
решению владельца продукта в скоуп идёт вся стройка целиком, без сужения
под нишу пилота (капремонт).

### Сопоставление профиля клиента с закупкой

```python
from classifier import ConstructionClassifier, find_matching_tenders
from classifier.sample_tenders import SAMPLE_TENDERS

classifier = ConstructionClassifier()
results = find_matching_tenders(client_profile, SAMPLE_TENDERS, classifier)

best = results[0]
print(best.tender.name, best.is_match, best.score)
for reason in best.failed_reasons:
    print("не подходит:", reason)
```

`match_profile_to_tender()` проверяет: относится ли ОКПД2 закупки к
строительству, совпадает ли регион клиента (`profile.region_code`) с
регионом закупки, выполнено ли требование по СРО, достаточно ли опыта
(`years_of_experience`), заявлены ли мощности и не превышает ли НМЦК
среднегодовую выручку клиента. Последний критерий (финансовый) — заглушка
для прототипа: настоящая формула скоринга — предмет ТЗ Агента 5, здесь
она нужна только чтобы результат на тестовых данных был осмысленным.

`SAMPLE_TENDERS` (`src/classifier/sample_tenders.py`) — придуманные
закупки по образцу реальных строительных тендеров 44-ФЗ по всем 4
регионам пилота, для демонстрации и тестов — не настоящие данные из ЕИС
(Агент 1 их пока не отдаёт в таком структурированном виде).

## Сборщик документов (Агент 6) — каркас

```python
from document_assembler import assemble_document_package

# profile.status должен быть READY (см. Агент 11 выше) — иначе ValueError
package = assemble_document_package(profile, tender)

for f in package.fields:
    print(f.name, "<-", f.source, "=", f.value, f"[{f.status}]")

if not package.is_complete():
    print("Не хватает:", [f.name for f in package.missing_fields()])
```

`assemble_document_package()` — это каркас, не генератор документов: он не
пишет содержимое (это будущая зона ответственности Агента 3 — Аналитика
документации, который не специфицирован), а только фиксирует, какие поля
пакета нужны и откуда каждое берётся (`source`, например `"legal.inn"`
или `"tender.max_price"`). Статус поля — `ready` / `missing` /
`not_applicable` (например, номер СРО не нужен, если закупка его не
требует). Если профиль клиента не в статусе `READY` — жёсткая ошибка
`ValueError`, без тихого пропуска шага, в соответствии с протоколом
контроля качества.
