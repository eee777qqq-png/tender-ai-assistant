# Тендерный ИИ-ассистент — контекст проекта

Этот файл читается автоматически в начале каждой сессии Claude Code. Здесь — суть проекта, чтобы не объяснять заново каждый раз.

## Глоссарий терминов Edwin

- **«Хакер»** — Claude Code, запущенный локально на компьютере Edwin (терминал/CLI), который гоняет диагностику/прогоны прямо на реальных данных (например, круг 2 бенчмарка Агента 4). Отдельная сессия от той, что работает через claude.ai/Cowork с доступом к его компьютеру через device bridge. Edwin вручную копирует результаты между двумя сессиями, прямого канала между ними нет. Когда Edwin просит «команды для хакера» — это значит: текст, который нужно вставить в терминал/чат Claude Code на его компьютере, а не выполнить самой.

## О продукте

Автоматизация подготовки к участию в госзакупках (44-ФЗ/223-ФЗ) для малого и среднего бизнеса (СМСП). Два сегмента: малому бизнесу — полный аутсорс под ключ, среднему — инструмент усиления штатного тендерного специалиста.

## Пилот

- **Ниша:** строительные работы / капремонт
- **Регионы:** Москва, Московская область, Краснодарский край, Ростовская область (без Крыма и Севастополя)
- **Владелец продукта:** Edwin — не разработчик, принимает бизнес-решения, лично выступает экспертом-проверяющим на пилоте (проверяет смету и документацию до момента, пока агенты не наберут статистику для перехода на выборочный аудит)
- **Юридическая форма:** сейчас ИП Edwin, только для собственного тестирования и 2-3 друзей. Полный переход на ООО (новые ЭЦП, перерегистрация в ЕИС, новые договоры, новый расчётный счёт, новый оператор персданных) — делается единым пакетом непосредственно перед открытием для внешних клиентов, не раньше и не по частям.

   **Первый настоящий тест на реальном документе — 2026-09-25, результат конкретный: экстрактор пропустил требование целиком, ложных срабатываний не дал.** Реальный текст — приложение «Требования к заявке» тендера №0373100134626000473 (2026-09-25 скачано вручную Edwin через браузер; с 2026-09-26 скачивается полностью автоматически — см. «Решено» ниже, `eis_client.attachment_analyst.fetch_participant_requirements()`). Причина не в баге, а в формате: реальное требование к опыту сформулировано не как «опыт не менее N лет» (единственный формат, который понимает `_EXPERIENCE_RE`), а как «опыт исполнения договора по текущему ремонту/капремонту/строительству, ЦЕНА которого — не менее 20% от НМЦК закупки» — стандартная формулировка доп. требования по ч.1.1 ст. 31 44-ФЗ (постановление Правительства №2571) для капстроительства/капремонта, не встречавшаяся ни в одном из трёх придуманных `sample_documents.py`. Дополнительная сложность для будущей регулярки — сама фраза с процентом («Цена выполненных работ... должна составлять не менее 20 процентов...») лежит в ОТДЕЛЬНОМ предложении от слова «опыт» (экстрактор разбирает текст по предложениям, `_sentences()`), то есть naive добавление процента в `_EXPERIENCE_RE` (которая требует триггер «опыт» и число в одном предложении) не сработает — нужен отдельный, самодостаточный паттерн по характерной фразе «цена выполненных работ ... не менее N процентов ... цены контракта», без обязательной связки со словом «опыт» в том же предложении. Честная хорошая новость: SRO в этом документе действительно не упоминается — экстрактор корректно вернул пустой список, а не ложное срабатывание; предложенное расширение НЕ реализовано в этой сессии по прямой просьбе владельца (сначала показать, как есть, потом решать) — новый паттерн добавлялся бы РЯДОМ с `_EXPERIENCE_RE`, не вместо неё (оба формата — варианты одного и того же `kind="experience"`, downstream-код в `document_assembler.assembler.py` проверяет только факт наличия требования этого вида, не текст/число, так что добавление новой регулярки безопасно для остального конвейера). Насколько распространён именно такой формат в реальных закупках капремонта (наш пилотный сегмент) — по одному документу не установить; следующий реальный документ вполне может принести третий, ещё не виденный вариант формулировки — ровно то, ради чего этот пункт остаётся открытым, а не решённым одной новой регуляркой.

      - **Реальная причина оказалась глубже предложенной гипотезы.** Дело было не в том, что технический токен «весит как обычное слово» — он вообще НЕ ДОХОДИЛ до сравнения: фильтр `tokenize_words()` `len(word) >= 3` (рассчитанный на отсев шумных обрывков/союзов) отсекал короткие числа («20», «40», «75», «32», «1») ещё ДО подсчёта пересечения — «20-40» и «5(3)-10» распадались на токены короче 3 символов и попросту исчезали из множества слов ОБЕИХ сторон, после чего правильный и ошибочный кандидат совпадали дословно (score 1.0 у обоих — добавлять вес было уже нечему). Исправлено: фильтр по длине применяется теперь только к токенам БЕЗ цифры.
      - **Предложенный вес ×3 для технического токена — реализован, проверен и ОСОЗНАННО ОТКЛОНЁН, не на глаз, а прогоном на обоих реальных документах целиком (все 42 строки, полный каталог 34004 работ + 45847 материалов).** Интуиция «несовпадение цифры должно штрафовать сильнее» на практике вредила: однозначные цифры («2» — группа грунта, «1» — количество) крайне частые и почти всегда СЛУЧАЙНО совпадают с несвязанными позициями каталога — вес усиливал шум, не сигнал. Перебор вариантов: без доп. веса (только фикс длины) — 66,7%; вес ×3, включая однозначные цифры — 52,4% (ХУЖЕ базового); вес ×3, только числа от 2 цифр — 54,8%; вес ×2, только числа от 2 цифр — 66,7% (не лучше, чем без веса); вес ×5 — 50,0% (хуже всех). **Итоговая реализация — без отдельного веса, только фикс `tokenize_words()`** (`_overlap_score()` — простое пересечение, как и было, только с исправленной токенизацией).

      - **Оба остаточных подкласса — разобраны и закрыты (один реализацией, второй честным отказом), 2026-09-29, продолжение той же сессии.**
        - **Подкласс 1 (однобуквенные/римские маркеры — «тип Б, марка II» vs «тип А, марка I»; «I класс» vs «II класс») — РЕАЛИЗОВАН.** Та же причина, что и у цифр: маркер марки/типа/класса в одну букву («Б», «А») или римским числом («I», «II») короче 3 символов отсекался тем же фильтром `len(word) >= 3`, что раньше отсекал короткие числа. `tokenize_words()` теперь не отсекает и такие токены — `_SINGLE_LETTER_RE` (однобуквенный кириллический/латинский токен, не входящий в `_STOPWORDS` — частые предлоги-однобуквенные слова, включая «и», уже отсекаются стоп-листом ДО этой проверки, риск спутать римское «I» с союзом «и» не подтвердился: это разные символы Unicode) и `_ROMAN_NUMERAL_RE` (I..XX по паттерну, не по фиксированному списку). У этого пункта, в отличие от остальных, третий вариант ответа — `e` (внести правку): для многострочного текста `input()` в терминале не годится, поэтому скрипт пишет исходный текст в файл `data/review_draft_<id>.txt`, ждёт, пока эксперт отредактирует и сохранит его в обычном текстовом редакторе, затем читает файл обратно и сохраняет как `corrected_output` — с выбором, одобрить ли исправленную версию или отклонить оригинал, оставив правку только образцом на будущее.

## Протокол контроля качества — обязательные правила, без исключений

- Выдача агентов 3, 4, 6 (документация, смета, пакет документов) не уходит клиенту без подтверждения эксперта-человека, пока не накоплена статистика и не согласован переход на выборочный аудит.
- Профиль клиента (агент 11) проверяется на полноту и достоверность до того, как им пользуется агент 6.
- Любое обновление нормативной базы (агент 10) применяется только после подтверждения эксперта — автоматическое применение запрещено.
- **Автоматическая подача заявки и автоматическая подпись КЭП без участия собственника — исключены архитектурно.** Не реализовывать эту функциональность ни в каком виде, даже как опцию.
- Если агент выдаёт смету/документацию — обязательно указывать дату актуальности нормативных данных, на которые опирается расчёт.

## Технические решения, уже принятые

- Продукт: сайт (веб-приложение) + Telegram-бот. Нативные iOS/Android — не на старте.
- Источник данных ЕИС: официальный доступ через zakupki.gov.ru, регистрация как «физическое лицо, индивидуальный предприниматель» → токен (не mTLS-сертификат, это только для юрлиц). Переменная `EIS_CONSUMER_TYPE=individual_person`. Не FTP, не HTML-скрапинг — ненадёжно и неполно по НМЦК; открытый FTP ЕИС закрыт с 01.01.2025.
- Метрика готовности агента к переходу с полной проверки эксперта на выборочный аудит (применяется к агентам 3, 4, 6): скользящее окно 50 проверок, ≥90% без существенной корректировки, 0 критических ошибок, откат при любой критической ошибке после перехода.
- **Хостинг для Агента 1 (монитор) — не облако, а личный компьютер Edwin (Windows), пересмотрено 2026-09-27.** Изначальный план (Railway, затем как альтернатива — Timeweb Cloud VPS) отменён по факту, не по предпочтению: `zakupki.gov.ru`/`int.zakupki.gov.ru` блокирует TCP-соединения с ЛЮБЫХ датацентр/облачных IP-диапазонов на сетевом уровне (подтверждено идентичным поведением на двух независимых окружениях — песочнице Claude и Timeweb VPS: DNS резолвится, обычный интернет работает, но соединение именно к EIS API молча зависает; `traceroute` показывает пропажу пакетов без ICMP-ответа после определённого хопа — сигнатура намеренной фильтрации, не случайного сбоя). Единственная среда за всё время проекта, откуда EIS API реально работал — домашний компьютер Edwin (обычный жилой IP), он же теперь и единственный источник данных для Агента 1: `run_monitor.py` запускается через штатный Планировщик заданий Windows ежедневно в 3:00, база `data/monitor.sqlite3` живёт локально на этом компьютере, объём данных тривиален (десятки КБ/день, до всего проекта — единицы-десятки МБ/год), место на диске не является ограничением. **Timeweb VPS (`104.171.136.126`, Новосибирск) остаётся оплаченным (до 28.10.2026) и в резерве** — не для мониторинга ЕИС (там он технически не работает), а на будущее под задачи, не требующие обращения к ЕИС с сервера напрямую (например, хранение документов клиентов, будущая клиент-facing инфраструктура, независимая от того, включён ли конкретно компьютер Edwin). **Незакрытая техническая задолженность:** root-пароль от Timeweb был единожды показан открытым текстом в переписке с Claude — подлежит смене перед тем, как сервер реально начнут использовать (не срочно, пока сервер простаивает).

  **Решение владельца на будущее, зафиксировано 2026-09-28 (не делать сейчас, только когда наступит момент):** при переходе на ООО и параллельном ведении нескольких клиентов — поставить отдельное выделенное железо (мини-ПК/старый ноутбук в headless-режиме, без монитора, ~3-8 тыс. руб. разово) на обычном домашнем/офисном интернете именно под Агента 1, отдельно от личного компьютера Edwin. Причина: домашний IP — единственное, что реально работает с ЕИС (см. выше), а личный рабочий ноутбук как постоянная продакшен-инфраструктура не годится (выключат/увезут/переустановят — монитор встанет незаметно). Разбирались и с альтернативами — резидентные прокси поверх Timeweb (~$5-30/мес при нашем объёме трафика 1-5 ГБ/мес, IPRoyal/Froxy и подобные) технически возможны, но дороже в долгосрочную и добавляют зависимость от стороннего сервиса; выделенное железо дома — дешевле (окупается в первый месяц) и решение установлено владельцем как приоритетное на момент этой записи. Ничего не менять до фактического перехода на ООО — текущий личный компьютер для стадии пилота (2-3 знакомых) достаточен.
- Агент 10 (Парсер нормативки, `src/regulatory_updates`): подтверждение экспертом обязательно для абсолютно каждой версии источника, включая самую первую («нулевую», когда предшественника ещё нет) — осознанное решение владельца, не временная заглушка. **Заметка на будущее, не сейчас:** если на практике подтверждать по одной 10-15 региональных версий вручную окажется неудобно, можно добавить пакетное подтверждение (одобрить сразу несколько `PENDING`-записей одним действием) — это только ускорение самого процесса подтверждения, саму обязательность экспертной проверки такая доработка не отменяет.
- Налоговый режим в профиле клиента (Агент 11, `onboarding.tax_config`): вместо свободного текста «система налогообложения» + отдельного дохода, из которых сервису пришлось бы самому вычислять ставку НДС и следить за порогами/индексацией УСН — клиент выбирает готовую комбинацию режим+ставка сам, из ровно 9 фиксированных вариантов (`TaxRegimeChoice`: УСН 6%/15% без НДС или с НДС 5%/7%, ОСН+НДС 22% отдельно для ИП и для ООО — разделено 2026-09-25, разные налоги с одного дохода, см. «Известные пробелы», п.6 — либо «другое — уточнить с бухгалтером»). Агент 5 (когда будет спроектирован) берёт ставку прямо из этого выбора, не вычисляет её. `tax_config.py` — справочник для валидации выбора в форме, не калькулятор; там же `UNVERIFIED_NOTES` с непроверенной информацией о возможном возврате ставки НДС к 20% с 2027 года — заметка на будущее, автоматически ничего не меняет. Среднегодовая выручка (`avg_annual_revenue`) осталась отдельным полем для другой цели — финансовой состоятельности клиента у Агента 2, с налоговым режимом не связана.

## Стиль работы

- Объяснять технические шаги простыми словами — владелец не разработчик.
- Не делать необратимых или дорогостоящих шагов (деплой в прод, трата денег на подписки/API) без явного подтверждения.
- Каждое техническое решение сверять с протоколом контроля качества выше.
- Коммитить и пушить в GitHub после каждого законченного куска работы, не ждать полной готовности всего агента.
- **Эскалационная дисциплина перед вопросом к владельцу (2026-09-29, прямое требование):** прежде чем сказать «нужно решение владельца» — сначала самостоятельно исчерпать несколько (2-3+) независимых способов найти ответ (веб-поиск с разными формулировками, документация источника, чтение кода/данных). Если один способ не сработал — пробовать следующий, а не сразу эскалировать. Только когда несколько реальных вариантов действий исчерпаны и вопрос объективно требует решения человека (ресурсы, приоритет, юридическая/бизнес-развилка) — тогда идти к владельцу с чётко сформулированной развилкой, а не расплывчатым «нужно решение».
