# Тендерный ИИ-ассистент — контекст проекта

Этот файл читается автоматически в начале каждой сессии Claude Code. Здесь — суть проекта, чтобы не объяснять заново каждый раз.

## О продукте

Автоматизация подготовки к участию в госзакупках (44-ФЗ/223-ФЗ) для малого и среднего бизнеса (СМСП). Два сегмента: малому бизнесу — полный аутсорс под ключ, среднему — инструмент усиления штатного тендерного специалиста.

## Пилот

- **Ниша:** строительные работы / капремонт
- **Регионы:** Москва, Московская область, Краснодарский край, Ростовская область (без Крыма и Севастополя)
- **Владелец продукта:** Edwin — не разработчик, принимает бизнес-решения, лично выступает экспертом-проверяющим на пилоте (проверяет смету и документацию до момента, пока агенты не наберут статистику для перехода на выборочный аудит)
- **Юридическая форма:** сейчас ИП Edwin, только для собственного тестирования и 2-3 друзей. Полный переход на ООО (новые ЭЦП, перерегистрация в ЕИС, новые договоры, новый расчётный счёт, новый оператор персданных) — делается единым пакетом непосредственно перед открытием для внешних клиентов, не раньше и не по частям.

Изменений нет. Похоже на то, что доступ по токену ещё не полностью активирован на стороне ЕИС — не подтверждено. Следующий шаг — Edwin проверяет статус токена в личном кабинете ЕИС и/или обращается в поддержку ЕИС с этим симптомом. Подробности — README.md, раздел «Что сервис умеет и чего не умеет».

Точный код — в закрытом «Альбоме ТФФ ЕИС», не входит в общедоступный документ.
5. **Агент 6 (Сборщик документов)** (`src/document_assembler`) — технически подключён к Агенту 3 (`extracted_requirements` дополняет обязательность полей, скрытые риски прокидываются в `DocumentPackage.hidden_risks`), но содержательной генерации документов всё ещё нет — источником текста самих документов Агент 3 в его нынешнем виде (структурированное извлечение требований) не является, это отдельная нерешённая задача.
6. **Метод извлечения требований в Агенте 3** (`src/document_analyst/extractor.py`) — не выбран. Сейчас это эвристический поиск по ключевым словам/регулярным выражениям, подобранный под три придуманных тестовых документа (`sample_documents.py`), а не под реальную документацию закупок с произвольными формулировками. Нет решения, будет ли это LLM-экстракция, промышленный NLP-парсер или что-то ещё — именно поэтому 100% выдачи идёт через эксперта (протокол ниже), пока не накоплена статистика на реальных документах.
7. **Перевод скрытых рисков в понятный текст для собственника в Агенте 8** (`src/client_consultant/consultant.py`, `_RISK_PRACTICAL_MEANING`) — сейчас 5 фиксированных шаблонов, по одному на каждую категорию риска (`RiskCategory`), без учёта конкретной цитаты/цифр из конкретной находки — общий смысл категории, не интеллектуальный пересказ. Так же и подсказки «что сделать» для недостающих полей (`_ACTION_HINTS`) — фиксированный словарь по именам полей, которые сейчас строит Агент 6; новое поле или новая категория риска потребует вручную добавить текст, автоматического пересказа произвольного текста нет. Решения, нужен ли здесь LLM для более живого пересказа, не принято.
8. **Тексты Агента 12 (границы ответственности) не проверены юристом.** И `CLIENT_SUMMARY_LEGAL_NOTICE` (`src/legal_boundaries/notices.py`, вшито в вывод Агента 8) для интерфейса, и черновик формулировки для будущего договора-оферты (`docs/legal-boundary-draft.md`) — рабочие варианты владельца продукта, не формулировки, подготовленные или проверенные практикующим юристом. Использовать черновик из `docs/legal-boundary-draft.md` в реальном договоре или другом документе с юридической силой для внешних клиентов нельзя до юридической проверки — см. пометку в самом файле.

## Архитектура — 12 агентов

Не универсальный бот, а конвейер специализированных агентов. Для каждого агента должно быть явно зафиксировано: источник входных данных, формат выхода, критерий готовности, нужен ли человек-эксперт перед выдачей клиенту.

| № | Агент | Статус |
|---|---|---|
| 1 | Монитор (сбор данных ЕИС) | Реализован по подтверждённому протоколу (`src/eis_client`, см. официальную инструкцию 2025 в `docs/`). Токен физлица получен, TLS/сеть отлажены (см. «Известные пробелы», п.3) — но реальные данные пока не приходят (сервис отвечает эхом запроса, а не `archiveUrl`), причина не подтверждена. Плюс не уточнён точный код реестра извещений (не контрактов) по Альбому ТФФ ЕИС (см. п.4 там же). Открытый FTP ЕИС закрыт с 01.01.2025 — не рабочий вариант |
| 2 | Классификатор (фильтр под клиента) | Реализован (`src/classifier`) — весь официальный раздел ОКПД2 «Строительство» (коды 41/42/43, 548 записей, источник — файл владельца `okpd.xlsx`). Решение владельца: без сужения, вся стройка в скоуп. Плюс сопоставление профиля клиента с конкретной закупкой (регион/СРО/опыт/финансы) на придуманных тестовых закупках — реальных данных из ЕИС для этого пока нет |
| 3 | Аналитик документации | В работе — каркас (`src/document_analyst`): извлекает из текста документации закупки сроки подачи/исполнения, требования к обеспечению заявки/контракта, требования к участнику и отдельно помеченный список «скрытых рисков» (нестандартные штрафы, безлимитная неустойка, одностороннее право заказчика, расплывчатые формулировки). Извлечение — эвристика по ключевым словам/regex на трёх придуманных тестовых документах, метод для реальных документов не выбран (см. «Известные пробелы»). Подключена та же логика аудита, что для Агента 4: `AuditReadinessTracker`/`AuditReadinessRegistry` (`src/quality_control`) + новый категоризированный лог расхождений `CategorizedDiscrepancyLog` (критическая/существенная/косметическая + что пропущено/неверно + комментарий эксперта) — пока структура для будущего заполнения экспертом, без готовой интеграции. **Технически подключён к Агенту 6** через `extracted_requirements` (`assemble_document_package(profile, tender, extracted_requirements=...)`) — обязательность полей обеспечения/допусков в пакете теперь учитывает и то, что извлёк Агент 3, не только структурированные поля `Tender`; скрытые риски прокидываются в `DocumentPackage.hidden_risks` для будущего Агента 8. Подключение требует `ExtractedRequirements.expert_reviewed=True` (жёсткая ошибка иначе) — проверка экспертом не автоматизирована |
| 4 | Сметчик (ФЕР/ТЕР/ГЭСН) | ТЗ готово, инфраструктура контроля качества реализована в `src/quality_control` (метрика выборочного аудита + лог расхождений). Сам расчёт сметы не реализован — источник нормативки в процессе (запрос отправлен в Сметрикс на B2B/API, ждём ответ). Найдена бесплатная альтернатива/дополнение — гос. ФГИС ЦС (fgiscs.minstroyrf.ru), но там подтверждён только веб-интерфейс через Госуслуги + платный крипто-клиент (Jinn-Client/Континент, ~7000₽), задокументированного bulk-API не нашли — не проверено на практике |
| 5 | Скоринг вероятности победы | Не специфицирован. Cold start — своей истории побед/поражений ещё нет |
| 6 | Сборщик документов | В работе — каркас (`src/document_assembler`): проверка статуса профиля READY (жёсткая ошибка, если не READY) + заготовка полей пакета с указанием источника каждого поля. Теперь принимает необязательный `extracted_requirements` от Агента 3 (сроки/обеспечение/допуски/скрытые риски) и учитывает его при определении обязательности полей — например, обеспечение исполнения контракта, которого вообще нет в `Tender`. Содержательная генерация документов по-прежнему не реализована. Метрика готовности к выборочному аудиту уже реализована в `src/quality_control` |
| 7 | Проверка комплектности | В работе — каркас (`src/completeness_check`): берёт заготовку пакета от агента 6 и данные закупки, сверяет, что пакет относится к этой закупке, и выносит вердикт PASS/FAIL по обязательным полям с конкретным списком недостающих (плюс отдельный информационный список недостающих необязательных). Работает на признаке `required` в `PackageField` (агент 6 теперь его сохраняет, а не отбрасывает) |
| 8 | Консультант для клиента | В работе — каркас (`src/client_consultant`): берёт результат всей цепочки — матчинг закупки от агента 2, вердикт комплектности от агента 7, пакет документов от агента 6 (в нём же — скрытые риски агента 3) — и собирает сводку для собственника простыми словами: подходит ли закупка, готовы ли документы, что конкретно не хватает и что с этим делать, каждый скрытый риск — с переводом «что это значит на практике». Ничего не рекомендует и не решает, явное напоминание об этом — в каждой сводке. Защиты от невыверенных экспертом данных Агента 3 отдельно не делали — она уже наследуется от Агента 6 (`assemble_document_package` не даст собрать пакет со скрытыми рисками без `expert_reviewed=True`) |
| 9 | Клиентская аналитика | Не специфицирован |
| 10 | Парсер нормативки | В работе — каркас (`src/regulatory_updates`): отслеживает два типа источников — базу расценок (ФЕР/ТЕР/ГЭСН, региональные индексы) и законодательство (44-ФЗ/223-ФЗ). Хранит текущую применённую версию каждого источника в SQLite (`RegulatoryUpdateStore`, по аналогии с `MonitorStore` у Агента 1) и при обнаружении новой версии строит явный diff по пунктам (старое значение → новое). Новая версия никогда не применяется автоматически — `detect_update()` только создаёт запись со статусом `PENDING`; применяет её `apply_update()`, который сам отказывается работать, пока запись не переведена в `APPROVED` через `approve_update(reviewer, approved=True/False)`. Отклонение обязательно требует причины, которая фиксируется в записи (`decision_reason`) и доступна через `list_rejected()` для анализа, по аналогии с логом расхождений Агента 4. Тестовые версии источников — придуманные, но реалистичные (`sample_versions.py`), реального источника пока нет (см. п.2 «Известных пробелов»). Интерфейс для решения эксперта — `src/review_queue.py` (см. ниже) |
| 11 | Онбординг клиента (профиль) | Реализован в коде (`src/onboarding`) — 4 блока полей (юр.данные, допуски/опыт, мощности, финансовая готовность) + статусная модель `черновик → заполнен → проверен экспертом → готов`, переход на последние две стадии — ручное действие человека, не автоматика |
| 12 | Юрист по договору с клиентом сервиса (границы ответственности) | Реализован каркас (`src/legal_boundaries`) — фиксированный текст `CLIENT_SUMMARY_LEGAL_NOTICE` (сервис не гарантирует победу, решение всегда за собственником, ответственность за устаревшие неподтверждённые данные профиля — не на сервисе), безусловно вшитый в конец `render_summary_text()` Агента 8 как неотъемлемая часть функции, а не опциональный параметр. Отдельно — черновик более формальной формулировки для будущего договора-оферты (`docs/legal-boundary-draft.md`). Оба текста не проверены юристом (см. «Известные пробелы», п.8) |

## Интерфейс эксперта-проверяющего

- `src/review_queue.py` — интерактивный CLI (не сайт): показывает всё, что ждёт решения Edwin, и даёт ответить да/нет прямо в терминале, не трогая код.
  - Реальная очередь: все записи `PENDING` у Агента 10 (`RegulatoryUpdateStore.list_pending()`) — с diff по пунктам и настоящим `approve_update()`/отклонением с причиной.
  - Учебный пример, не реальная очередь: три тестовых документа Агента 3 (`sample_documents.py`), прогнанные через `extract_requirements()` при каждом запуске — подтверждение только помечает объект в памяти, отклонение только печатается в терминал (у Агента 3 нет постоянного хранилища результатов, см. «Известные пробелы»).
- **Заметка на будущее, не сейчас:** терминал годится, пока проверяющий — один человек (Edwin) и очередь короткая. Если объём вырастет или проверяющих станет больше, для реального интерфейса может понадобиться что-то удобнее — веб-страница в самом продукте или общая Google-таблица с формулами/фильтрами. Явного решения пока нет, `review_queue.py` — временное практичное решение под текущий масштаб пилота.

## Протокол контроля качества — обязательные правила, без исключений

- Выдача агентов 3, 4, 6 (документация, смета, пакет документов) не уходит клиенту без подтверждения эксперта-человека, пока не накоплена статистика и не согласован переход на выборочный аудит.
- Профиль клиента (агент 11) проверяется на полноту и достоверность до того, как им пользуется агент 6.
- Любое обновление нормативной базы (агент 10) применяется только после подтверждения эксперта — автоматическое применение запрещено.
- **Автоматическая подача заявки и автоматическая подпись КЭП без участия собственника — исключены архитектурно.** Не реализовывать эту функциональность ни в каком виде, даже как опцию.
- Если агент выдаёт смету/документацию — обязательно указывать дату актуальности нормативных данных, на которые опирается расчёт.

## Технические решения, уже принятые

- Продукт: сайт (веб-приложение) + Telegram-бот. Нативные iOS/Android — не на старте.
- Источник данных ЕИС: официальный доступ через zakupki.gov.ru, регистрация как «физическое лицо, индивидуальный предприниматель» → токен (не mTLS-сертификат, это только для юрлиц). Переменная `EIS_CONSUMER_TYPE=individual_person`. Не FTP, не HTML-скрапинг — ненадёжно и неполно по НМЦК; открытый FTP ЕИС закрыт с 01.01.2025.
- Метрика готовности агента к переходу с полной проверки эксперта на выборочный аудит (применяется к агентам 3, 4, 6): скользящее окно 50 проверок, ≥90% без существенной корректировки, 0 критических ошибок, откат при любой критической ошибке после перехода.
- Хостинг для постоянно работающих агентов (монитор и далее) — Railway, отдельный новый проект на существующем аккаунте Edwin, не смешивать с другими его проектами.
- Агент 10 (Парсер нормативки, `src/regulatory_updates`): подтверждение экспертом обязательно для абсолютно каждой версии источника, включая самую первую («нулевую», когда предшественника ещё нет) — осознанное решение владельца, не временная заглушка. **Заметка на будущее, не сейчас:** если на практике подтверждать по одной 10-15 региональных версий вручную окажется неудобно, можно добавить пакетное подтверждение (одобрить сразу несколько `PENDING`-записей одним действием) — это только ускорение самого процесса подтверждения, саму обязательность экспертной проверки такая доработка не отменяет.
