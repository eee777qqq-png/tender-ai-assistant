# Тендерный ИИ-ассистент — контекст проекта

Этот файл читается автоматически в начале каждой сессии Claude Code. Здесь — суть проекта, чтобы не объяснять заново каждый раз.

## О продукте

Автоматизация подготовки к участию в госзакупках (44-ФЗ/223-ФЗ) для малого и среднего бизнеса (СМСП). Два сегмента: малому бизнесу — полный аутсорс под ключ, среднему — инструмент усиления штатного тендерного специалиста.

## Пилот

- **Ниша:** строительные работы / капремонт
- **Регионы:** Москва, Московская область, Краснодарский край, Ростовская область (без Крыма и Севастополя)
- **Владелец продукта:** Edwin — не разработчик, принимает бизнес-решения, лично выступает экспертом-проверяющим на пилоте (проверяет смету и документацию до момента, пока агенты не наберут статистику для перехода на выборочный аудит)
- **Юридическая форма:** сейчас ИП Edwin, только для собственного тестирования и 2-3 друзей. Полный переход на ООО (новые ЭЦП, перерегистрация в ЕИС, новые договоры, новый расчётный счёт, новый оператор персданных) — делается единым пакетом непосредственно перед открытием для внешних клиентов, не раньше и не по частям.

9. **Таблица «налоговый режим клиента → сумма налога в рублях» в Агенте 5** (`src/profitability_estimator/estimator.py`, `_TAX_RULES`) не проверена бухгалтером. Рабочее приближение Claude: НДС везде считается от полной НМЦК без вычета входного НДС (для «ОСН + НДС 22% (с вычетом)» это неточно — вычитать не на чем, данных о затратах с НДС нет), налог на прибыль ОСН зафиксирован на стандартных 20% (не хранится в `TaxRegimeChoice`, клиенту в форме показана только ставка НДС), страховые взносы и прочие обязательные платежи не учтены. До проверки бухгалтером/владельцем — маржа Агента 5 показательная, не окончательная цифра для клиента.
10. **Оценка вероятности победы (изначально — сам Агент 5 в таблице ниже) отделена от оценки выгоды и не специфицирована.** Агент 5 сейчас считает только маржу и качественные флаги риска без цифр (`src/profitability_estimator`) — своей статистики побед/поражений ещё нет (cold start), вычислять число из непроверенных допущений решили не делать. Переход на числовую вероятность станет возможен только после того, как Агент 9 (клиентская аналитика, тоже не специфицирован) накопит статистику — как именно это будет работать, не спроектировано.
11. **Методологическая ошибка в расчёте региональной цены Агента 4 — найдена, диагностирована и исправлена, 2026-09-18.** Причина была ровно та, что и предполагалась: `index_parser.py` (удалён) парсил письма Минстроя с **общими индексами «к ФЕР-2001/ТЕР-2001»** — это индексы для другого, более старого базисно-индексного метода (база — цены 2001 года), а ФСНБ-2022 — ресурсно-индексный метод с базой **01.01.2022** (подтверждено официальным разъяснением Минстроя, приказ №1046/пр — тот же, которым утверждена сама ФСНБ-2022). Прямое умножение текущей `base_price` на индекс не того метода задваивало пересчёт. Исправление: найден и подключён правильный источник — «Индексы по группам однородных строительных ресурсов (ГОСР)» на `fgiscs.minstroyrf.ru/prices` (`src/smeta_estimator/regional_pricing_client.py` + `regional_pricing_parser.py`), масштаб значений (~1.2–2.7) на порядок отличается от прежних (~14–60), проверено на реальных данных Москвы. Плюс реализован приоритет из ТЗ: сначала текущая цена ресурса напрямую (если опубликована), иначе базисная цена × ГОСР-индекс для группы именно этого ресурса — не единый общий множитель на всю позицию (`pricing.py`, полностью переписан). Остаточные, более мелкие вопросы — пп.12–16 ниже.
12. **Трудозатраты — и рабочих, и машинистов — не оцениваются в `base_price`/региональной цене Агента 4.** Коды разрядов работ (`1-100-38` и подобные, агрегированный код «2») по-прежнему не имеют цены ни в ФСБЦ, ни в ГОСР. Дополнительно уточнено 2026-09-18: цена машино-часа в ФСБЦ хранится раздельно (`SalaryMach` — зарплата машиниста, `PriceCostWithoutSalary` — остальное), и в `base_price`/ГОСР-пересчёте участвует **только `PriceCostWithoutSalary`** — это подтверждено тем, что оно в точности совпадает с базисной ценой в отчёте ГОСР («без учёта оплаты труда машинистов»). И то, и другое трудозатраты требуют отдельного источника (открытый набор «Среднемесячные размеры оплаты труда» ФГИС ЦС, не подключён) — явно помечается через `unresolved`/`unpriced_resource_codes`, не молчаливый ноль.
13. **Часть материалов ГЭСН задана категорией, не конкретным продуктом** (`<AbstractResource>` в XML, `abstract_resource_codes` в `GesnWorkItem`) — например «Материалы рулонные кровельные для нижних слоев» без указания, что конкретно использовать. Выбор конкретного продукта и его цены — ручное решение эксперта, не автоматизировано; для кровельных работ это обычно основной материал, то есть региональная цена может занижать себестоимость особенно сильно именно там, где материал дороже всего.
14. **Покрытие ГОСР по машинам неполное — не для каждого кода ресурса есть строка в отчёте за конкретный квартал.** На реальном примере (Москва, 3 квартал 2026) из 5 машинных кодов тестовой позиции индекс нашёлся только для 2 — остальные (при том, что коды существуют в ФСБЦ) в этот раз просто не попали в отчёт ГОСР. Не ошибка парсинга — так устроен сам отчёт (публикуются далеко не все комбинации код×регион×квартал). Эти ресурсы честно остаются `unresolved`, но из-за этого региональная цена может быть занижена сильнее, чем кажется на первый взгляд.
15. **Полнота и постраничность API текущих цен (`fetch_current_prices_json`) не проверена на масштабе.** Работает по наблюдению: `take=100000` вернул все ~2700 позиций материалов Москвы одним запросом без дополнительной пагинации — не проверено, всегда ли так (для регионов/категорий с большим количеством позиций может понадобиться постраничная догрузка, сейчас не реализована). Поиск по коду ресурса через параметр `search=` не сработал при проверке (пустой результат) — сейчас используется полная выгрузка категории с последующим локальным поиском по коду, не серверная фильтрация.
16. **`DEFAULT_ARCHIVE_URL` (`fsnb_client.py`) и `CURRENT_PERIOD_ID` (`regional_pricing_client.py`) — захардкожены на конкретную версию/квартал (2026-09-18, 3 квартал 2026), не отслеживаются автоматически.** Обновлять вручную по мере выхода новых версий/кварталов, либо (лучше) завести для них то же отслеживание версий через Агента 10, что уже сделано для самих индексов ГОСР (`regional_pricing_parser.build_regulatory_version`).

  - Реальная очередь: все записи `PENDING` у Агента 10 (`RegulatoryUpdateStore.list_pending()`) — с diff по пунктам и настоящим `approve_update()`/отклонением с причиной.

Если объём вырастет или проверяющих станет больше, для реального интерфейса может понадобиться что-то удобнее — веб-страница в самом продукте или общая Google-таблица с формулами/фильтрами. Явного решения пока нет, `review_queue.py` — временное практичное решение под текущий масштаб пилота.

## Протокол контроля качества — обязательные правила, без исключений

- Выдача агентов 3, 4, 6 (документация, смета, пакет документов) не уходит клиенту без подтверждения эксперта-человека, пока не накоплена статистика и не согласован переход на выборочный аудит.
- Профиль клиента (агент 11) проверяется на полноту и достоверность до того, как им пользуется агент 6.
- Любое обновление нормативной базы (агент 10) применяется только после подтверждения эксперта — автоматическое применение запрещено.
- **Автоматическая подача заявки и автоматическая подпись КЭП без участия собственника — исключены архитектурно.** Не реализовывать эту функциональность ни в каком виде, даже как опцию.
- Если агент выдаёт смету/документацию — обязательно указывать дату актуальности нормативных данных, на которые опирается расчёт.

## Технические решения, уже принятые

- Продукт: сайт (веб-приложение) + Telegram-бот. Нативные iOS/Android — не на старте.
- Источник данных ЕИС: официальный доступ через zakupki.gov.ru, регистрация как «физическое лицо, индивидуальный предприниматель» → токен (не mTLS-сертификат, это только для юрлиц). Переменная `EIS_CONSUMER_TYPE=individual_person`. Не FTP, не HTML-скрапинг — ненадёжно и неполно по НМЦК; открытый FTP ЕИС закрыт с 01.01.2025.
- Метрика готовности агента к переходу с полной проверки эксперта на выборочный аудит (применяется к агентам 3, 4, 6): скользящее окно 50 проверок, ≥90% без существенной корректировки, 0 критических ошибок, откат при любой критической ошибке после перехода.
- Хостинг для постоянно работающих агентов (монитор и далее) — Railway, отдельный новый проект на существующем аккаунте Edwin, не смешивать с другими его проектами.
- Агент 10 (Парсер нормативки, `src/regulatory_updates`): подтверждение экспертом обязательно для абсолютно каждой версии источника, включая самую первую («нулевую», когда предшественника ещё нет) — осознанное решение владельца, не временная заглушка. **Заметка на будущее, не сейчас:** если на практике подтверждать по одной 10-15 региональных версий вручную окажется неудобно, можно добавить пакетное подтверждение (одобрить сразу несколько `PENDING`-записей одним действием) — это только ускорение самого процесса подтверждения, саму обязательность экспертной проверки такая доработка не отменяет.
- Налоговый режим в профиле клиента (Агент 11, `onboarding.tax_config`): вместо свободного текста «система налогообложения» + отдельного дохода, из которых сервису пришлось бы самому вычислять ставку НДС и следить за порогами/индексацией УСН — клиент выбирает готовую комбинацию режим+ставка сам, из ровно 8 фиксированных вариантов (`TaxRegimeChoice`: УСН 6%/15% без НДС или с НДС 5%/7%, ОСН+НДС 22%, либо «другое — уточнить с бухгалтером»). Агент 5 (когда будет спроектирован) берёт ставку прямо из этого выбора, не вычисляет её. `tax_config.py` — справочник для валидации выбора в форме, не калькулятор; там же `UNVERIFIED_NOTES` с непроверенной информацией о возможном возврате ставки НДС к 20% с 2027 года — заметка на будущее, автоматически ничего не меняет. Среднегодовая выручка (`avg_annual_revenue`) осталась отдельным полем для другой цели — финансовой состоятельности клиента у Агента 2, с налоговым режимом не связана.
