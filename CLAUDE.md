# Тендерный ИИ-ассистент — контекст проекта

Этот файл читается автоматически в начале каждой сессии Claude Code. Здесь — суть проекта, чтобы не объяснять заново каждый раз.

## О продукте

Автоматизация подготовки к участию в госзакупках (44-ФЗ/223-ФЗ) для малого и среднего бизнеса (СМСП). Два сегмента: малому бизнесу — полный аутсорс под ключ, среднему — инструмент усиления штатного тендерного специалиста.

## Пилот

- **Ниша:** строительные работы / капремонт
- **Регионы:** Москва, Московская область, Краснодарский край, Ростовская область (без Крыма и Севастополя)
- **Владелец продукта:** Edwin — не разработчик, принимает бизнес-решения, лично выступает экспертом-проверяющим на пилоте (проверяет смету и документацию до момента, пока агенты не наберут статистику для перехода на выборочный аудит)
- **Юридическая форма:** сейчас ИП Edwin, только для собственного тестирования и 2-3 друзей. Полный переход на ООО (новые ЭЦП, перерегистрация в ЕИС, новые договоры, новый расчётный счёт, новый оператор персданных) — делается единым пакетом непосредственно перед открытием для внешних клиентов, не раньше и не по частям.

3. **Метод извлечения требований в Агенте 3** (`src/document_analyst/extractor.py`) — не выбран. Сейчас это эвристический поиск по ключевым словам/регулярным выражениям, подобранный под три придуманных тестовых документа (`sample_documents.py`), а не под реальную документацию закупок с произвольными формулировками. Нет решения, будет ли это LLM-экстракция, промышленный NLP-парсер или что-то ещё — именно поэтому 100% выдачи идёт через эксперта (протокол ниже), пока не накоплена статистика на реальных документах.
4. **Перевод скрытых рисков в понятный текст для собственника в Агенте 8** (`src/client_consultant/consultant.py`) — частично улучшено 2026-09-25 (см. «Решено»), ядро вопроса не решено. Для 4 из 5 категорий риска (`UNCAPPED_LIABILITY`, `UNILATERAL_TERMS`, `AMBIGUOUS_CONDITION`, `OTHER`) по-прежнему один фиксированный шаблон на категорию (`_RISK_PRACTICAL_MEANING`), без учёта конкретной цитаты/цифр находки — общий смысл категории, не интеллектуальный пересказ; для этих категорий Агент 3 пока и не извлекает отдельных чисел (например, сумму неустойки), которые можно было бы подставить. Так же и подсказки «что сделать» для недостающих полей (`_ACTION_HINTS`) — фиксированный словарь по именам полей, которые сейчас строит Агент 6; новое поле или новая категория риска потребует вручную добавить текст, автоматического пересказа произвольного текста нет.

   Полноценный интеллектуальный пересказ произвольного текста находки (не подстановка уже готового числа, а свободный пересказ цитаты своими словами) потребовал бы LLM-вызова — решение, нужен ли он, не принято, ждёт подтверждения владельца. Если решение будет положительным, вот что потребуется:
   - **Точка вызова:** `_translate_risk()`/`_practical_meaning()` в `src/client_consultant/consultant.py` — один вызов на каждый `HiddenRisk` при сборке `ClientSummary` (Агент 8), не пакетно на весь документ и не на каждую закупку в потоке Агента 1 (риски пересказываются только на этапе сборки итоговой сводки, уже после того как закупка прошла фильтр Агента 2).
   - **Вход:** `risk.excerpt` (цитата) + `risk.explanation` (почему это риск) + категория — по несколько сотен символов на вызов.
   - **Порядок стоимости:** ориентировочно 200–400 входных и 100–200 выходных токенов на один риск при коротком промпте (пересказ на 2-3 предложения); типичная закупка даёт 1-2 риска (см. тестовые документы), значит единицы вызовов на одну клиентскую сводку. Точная цена зависит от выбранной модели — модель не выбрана, это отдельное решение.
   - **Контроль качества:** LLM-пересказ, как и любая другая выдача агентов 3/4/6, по протоколу (см. ниже) не может уходить клиенту без проверки эксперта — а сейчас сводка Агента 8 вообще не проходит через `review_queue.py` ни в каком виде, этот шаг для неё придётся сначала завести.
5. **Тексты Агента 12 (границы ответственности) не проверены юристом.** И `CLIENT_SUMMARY_LEGAL_NOTICE` (`src/legal_boundaries/notices.py`, вшито в вывод Агента 8) для интерфейса, и черновик формулировки для будущего договора-оферты (`docs/legal-boundary-draft.md`) — рабочие варианты владельца продукта, не формулировки, подготовленные или проверенные практикующим юристом. Использовать черновик из `docs/legal-boundary-draft.md` в реальном договоре или другом документе с юридической силой для внешних клиентов нельзя до юридической проверки — см. пометку в самом файле.
6. **Таблица «налоговый режим клиента → сумма налога в рублях» в Агенте 5** (`src/profitability_estimator/estimator.py`, `_TAX_RULES`) не проверена бухгалтером. Рабочее приближение Claude: НДС везде считается от полной НМЦК без вычета входного НДС (для «ОСН + НДС 22% (с вычетом)» это неточно — вычитать не на чем, данных о затратах с НДС нет), налог на прибыль ОСН зафиксирован на стандартных 20% (не хранится в `TaxRegimeChoice`, клиенту в форме показана только ставка НДС), страховые взносы и прочие обязательные платежи не учтены. До проверки бухгалтером/владельцем — маржа Агента 5 показательная, не окончательная цифра для клиента.
7. **Оценка вероятности победы (изначально — сам Агент 5 в таблице ниже) отделена от оценки выгоды и не специфицирована.** Агент 5 сейчас считает только маржу и качественные флаги риска без цифр (`src/profitability_estimator`) — своей статистики побед/поражений ещё нет (cold start), вычислять число из непроверенных допущений решили не делать. Переход на числовую вероятность станет возможен только после того, как Агент 9 (клиентская аналитика, тоже не специфицирован) накопит статистику — как именно это будет работать, не спроектировано.
8. **Агент 4 подключён к Агенту 5 (`src/smeta_estimator/cost_estimate.py`, 2026-09-18), но объём работ по смете конкретной закупки — не автоматизированный внешний вход, а ручной параметр (`SmetaLineItem.work_volume`).** Это единственное место в этой связке, где стык получился не таким гладким, как между Агентом 3 и Агентом 6: там Агент 3 сам извлекает из текста документации всё, что нужно Агенту 6. Здесь же ни Агент 3 (извлекает сроки/обеспечение/риски, не ведомость объёмов работ), ни Агент 4 (не реализовано — см. таблицу ниже) не считают, сколько именно "100 м2" кровли или "м3" бетона нужно по конкретной закупке — эту цифру по-прежнему подставляет человек. `build_cost_estimate()` требует `MatchResult.expert_reviewed=True` для каждой позиции (тот же гейт, что у Агента 3 в `assemble_document_package()`/`estimate_profitability()`) и передаёт себестоимость в `CostEstimate` с новыми полями `expert_reviewed`/`is_complete` — `estimate_profitability()` отказывает, если `expert_reviewed=False`, и добавляет риск-флаг, если `is_complete=False` (часть позиций сметы не оценена или оценена частично), не блокируя расчёт маржи целиком.
9. **`requires_sro`/`min_experience_years` — единственные 2 из 10 полей `Tender`, которые `notice_document_to_tender()` не извлекает из извещения** (остальные 8, включая реестровый номер/название/заказчика/НМЦК/сроки, закрыты реальным кодом 2026-09-24 — см. «Решено»; переход самого `run_monitor.py`/`.env` на извещения по умолчанию — тоже закрыт, см. «Решено»). Проверено на 463 реальных извещениях (Москва + Ростовская область) — ни одного тега, похожего на допуск СРО или минимальный опыт участника, не нашлось нигде; в извещении есть `preferensesInfo`/`requirementsInfo` со ссылками на статьи 44-ФЗ (`ET44`, `TR442` — «единые требования» и «доп. требования по ч.1.1 ст.31», без цифры/флага), но сами параметризованные значения либо лежат в приложенном PDF/DOCX (`attachmentsInfo`), не в XML, либо этой конкретной выборке (в основном мелкий текущий ремонт) доп. требования просто не полагаются — не проверено, какой вариант верный. Пока это не выяснено, `notice_document_to_tender()` принимает их обязательными параметрами (`requires_sro`, `min_experience_years`) без заглушки, всегда `False`/`0` в продакшене (`run_monitor.py`, `StoredTender.sro_experience_verified=False` явно помечает это как непроверенное) — `src/match_real_notices.py` передаёт их через флаги командной строки с тем же явным предупреждением в логе.

### Решено

Пункты ниже больше не открытые вопросы — оставлены для истории решений, не как активная работа. Нумерация внутри этого подраздела не связана с нумерацией открытых пунктов выше.

- **Частичное улучшение пересказа скрытых рисков в Агенте 8 — реализовано 2026-09-25, вопрос про LLM-пересказ остался открытым (см. открытый п.4).** Задача была не «решить, нужен ли LLM», а посмотреть, можно ли улучшить пересказ без него хотя бы частично — можно, для одной категории риска из пяти. `HiddenRisk` (`src/document_analyst/models.py`) получил новое поле `rate_pct: float | None = None` — извлечённое числовое значение находки; `extractor.py` заполняет его для `NONSTANDARD_PENALTY` (ставка штрафа/пени за день, уже разбиралась регуляркой `_PENALTY_RATE_RE`, просто раньше терялась после сборки строки `explanation` и не попадала в отдельное поле). Новая функция `_practical_meaning()` в `src/client_consultant/consultant.py` подставляет эту ставку в текст «что это значит на практике» вместо общей формулировки категории («Штраф за просрочку — 15% цены контракта за каждый день...» вместо «Штраф за просрочку выше обычного»), когда `rate_pct` заполнен; для остальных 4 категорий (`UNCAPPED_LIABILITY`/`UNILATERAL_TERMS`/`AMBIGUOUS_CONDITION`/`OTHER`) и для `NONSTANDARD_PENALTY` без `rate_pct` (не должно происходить сейчас, но на будущее) поведение не изменилось — прежний фиксированный шаблон `_RISK_PRACTICAL_MEANING[category]`. Не автоматический пересказ произвольного текста — точечная подстановка уже структурированного числа, которое агент и так извлекал, но раньше никуда не передавал дальше отдельным полем. `_ACTION_HINTS` (подсказки по недостающим полям) не трогали — вне скоупа этой задачи.
  - Тесты: `tests/test_document_analyst.py` — расширен существующий тест (`rate_pct == 15.0` для штрафа, `rate_pct is None` для расплывчатой формулировки той же закупки); `tests/test_client_consultant.py` — новый тест на реальном тестовом документе детсада (`SAMPLE_DOCUMENT_KINDERGARTEN`), проверяющий, что пересказ содержит именно «15%», а вторая находка (без извлечённого числа) — по-прежнему общий шаблон. Полный набор — 246 тестов, все проходят.
  - Полноценный интеллектуальный пересказ (свободный пересказ произвольной цитаты, не только подстановка уже найденного числа) требует LLM — не реализован, решение не принято, оценка стоимости/точки вызова зафиксирована в открытом п.4, ждёт подтверждения владельца.

- **Вся цепочка «получить настоящие документы закупок из ЕИС» — закрыта и подтверждена реальными данными, 2026-09-23.** Три независимые поломки шли одна за другой на одном и том же запросе (`python src/fetch_purchases.py --date 2026-09-21`, реестр контрактов, регион 77) — каждая маскировала следующую, пока не была исправлена: (1) неверный namespace в SOAP-конверте → сервис отвечал эхом запроса вместо ответа (EIS-891228); (2) GET за архивом без токена → 403 Forbidden; (3) поиск ОКПД2 по имени тега вместо реальной структуры документа → 0 найденных кодов из 1640 документов. Подробности каждой поломки и исправления — в отдельных записях ниже. **Итоговое подтверждение на реальном прогоне Edwin:** из 1640 XML-документов 674 содержат распознанный код ОКПД2, из них 8 — реальные строительные контракты за 2026-09-21 в Москве, с настоящими кодами (`41.20.40`, `43.22.12`, `43.29` и другими) и рабочими ссылками на документы. Монитор (Агент 1) на реальных данных ЕИС работает от SOAP-запроса до отбора закупок по стройке — это больше не каркас, это рабочая цепочка. **На момент этой записи (2026-09-23) три поля `Tender` (`requires_sro`, `min_experience_years`, `submission_deadline`) считались структурно недоступными в реестре контрактов** — реестровый номер (`_find_reestr_number()`) уже был подтверждён и исправлен в тот же день, см. отдельную запись ниже. **С 2026-09-24 картина точнее:** код реестра извещений подтверждён, `submission_deadline` (и ещё 5 полей) реально извлекается из извещения — см. отдельную запись про `notice_document_to_tender()` ниже; `requires_sro`/`min_experience_years` остаются недоступными и в извещении тоже (см. открытый п.9), это не было пробелом именно реестра контрактов, а более общая нехватка. **Важное предупреждение, не разовое:** даты, которые `run_monitor.py` пометил обработанными в `data/monitor.sqlite3`, пока сервис не работал (минимум с 2026-09-17 по 2026-09-23 — эхо, затем 403, затем нулевой ОКПД2-поиск), несут ЛОЖНЫЙ ноль документов, не честный «в этот день стройки не было». Перед тем как ставить `run_monitor.py` на регулярное расписание, эти даты нужно перезапросить вручную — опустошить `data/monitor.sqlite3` (или удалить конкретные строки) и прогнать `run_monitor.py --start-date` заново с 2026-09-17.

- **Код реестра ИЗВЕЩЕНИЙ (`PRIZ`/`epNotificationEF2020`) — гипотеза подтверждена реальным запросом, 2026-09-24, с первой попытки.** Прогнан ровно тот тест, который CLAUDE.md просил у Edwin («Следующий шаг» в прежней записи п.3): `EIS_SUBSYSTEM_TYPE=PRIZ`, `EIS_DOCUMENT_TYPE44=epNotificationEF2020`, переменные окружения при запуске, без правки `.env`. ## Протокол контроля качества — обязательные правила, без исключений

- Выдача агентов 3, 4, 6 (документация, смета, пакет документов) не уходит клиенту без подтверждения эксперта-человека, пока не накоплена статистика и не согласован переход на выборочный аудит.
- Профиль клиента (агент 11) проверяется на полноту и достоверность до того, как им пользуется агент 6.
- Любое обновление нормативной базы (агент 10) применяется только после подтверждения эксперта — автоматическое применение запрещено.
- **Автоматическая подача заявки и автоматическая подпись КЭП без участия собственника — исключены архитектурно.** Не реализовывать эту функциональность ни в каком виде, даже как опцию.
- Если агент выдаёт смету/документацию — обязательно указывать дату актуальности нормативных данных, на которые опирается расчёт.

## Технические решения, уже принятые

- Продукт: сайт (веб-приложение) + Telegram-бот. Нативные iOS/Android — не на старте.
- Источник данных ЕИС: официальный доступ через zakupki.gov.ru, регистрация как «физическое лицо, индивидуальный предприниматель» → токен (не mTLS-сертификат, это только для юрлиц). - Метрика готовности агента к переходу с полной проверки эксперта на выборочный аудит (применяется к агентам 3, 4, 6): скользящее окно 50 проверок, ≥90% без существенной корректировки, 0 критических ошибок, откат при любой критической ошибке после перехода.
- Хостинг для постоянно работающих агентов (монитор и далее) — Railway, отдельный новый проект на существующем аккаунте Edwin, не смешивать с другими его проектами.
- Агент 10 (Парсер нормативки, `src/regulatory_updates`): подтверждение экспертом обязательно для абсолютно каждой версии источника, включая самую первую («нулевую», когда предшественника ещё нет) — осознанное решение владельца, не временная заглушка. **Заметка на будущее, не сейчас:** если на практике подтверждать по одной 10-15 региональных версий вручную окажется неудобно, можно добавить пакетное подтверждение (одобрить сразу несколько `PENDING`-записей одним действием) — это только ускорение самого процесса подтверждения, саму обязательность экспертной проверки такая доработка не отменяет.
- Налоговый режим в профиле клиента (Агент 11, `onboarding.tax_config`): вместо свободного текста «система налогообложения» + отдельного дохода, из которых сервису пришлось бы самому вычислять ставку НДС и следить за порогами/индексацией УСН — клиент выбирает готовую комбинацию режим+ставка сам, из ровно 8 фиксированных вариантов (`TaxRegimeChoice`: УСН 6%/15% без НДС или с НДС 5%/7%, ОСН+НДС 22%, либо «другое — уточнить с бухгалтером»). Агент 5 (когда будет спроектирован) берёт ставку прямо из этого выбора, не вычисляет её. `tax_config.py` — справочник для валидации выбора в форме, не калькулятор; там же `UNVERIFIED_NOTES` с непроверенной информацией о возможном возврате ставки НДС к 20% с 2027 года — заметка на будущее, автоматически ничего не меняет. Среднегодовая выручка (`avg_annual_revenue`) осталась отдельным полем для другой цели — финансовой состоятельности клиента у Агента 2, с налоговым режимом не связана.

## Стиль работы

- Объяснять технические шаги простыми словами — владелец не разработчик.
- Не делать необратимых или дорогостоящих шагов (деплой в прод, трата денег на подписки/API) без явного подтверждения.
- Каждое техническое решение сверять с протоколом контроля качества выше.
- Коммитить и пушить в GitHub после каждого законченного куска работы, не ждать полной готовности всего агента.
