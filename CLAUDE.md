# Тендерный ИИ-ассистент — контекст проекта

Этот файл читается автоматически в начале каждой сессии Claude Code. Здесь — суть проекта, чтобы не объяснять заново каждый раз.

## О продукте

Автоматизация подготовки к участию в госзакупках (44-ФЗ/223-ФЗ) для малого и среднего бизнеса (СМСП). Два сегмента: малому бизнесу — полный аутсорс под ключ, среднему — инструмент усиления штатного тендерного специалиста.

## Пилот

- **Ниша:** строительные работы / капремонт
- **Регионы:** Москва, Московская область, Краснодарский край, Ростовская область (без Крыма и Севастополя)
- **Владелец продукта:** Edwin — не разработчик, принимает бизнес-решения, лично выступает экспертом-проверяющим на пилоте (проверяет смету и документацию до момента, пока агенты не наберут статистику для перехода на выборочный аудит)
- **Юридическая форма:** сейчас ИП Edwin, только для собственного тестирования и 2-3 друзей. Полный переход на ООО (новые ЭЦП, перерегистрация в ЕИС, новые договоры, новый расчётный счёт, новый оператор персданных) — делается единым пакетом непосредственно перед открытием для внешних клиентов, не раньше и не по частям.

**Реализовано в коде 2026-09-18 вечером, на основании устного подтверждения Smetrix (см. ниже) — не финально.** `pricing.py`/`fsnb_parser.py`/`models.py`: новый `MachineLabourInfo` (`parse_fsbc_machine_labour_xml`) хранит `LabourMach`/`DriverCode` по каждому машинному ресурсу; `price_candidate_for_region()` теперь принимает необязательный `machine_labour` и, если для ресурса `labour_mach > 0`, прибавляет `labour_mach × текущая_ставка(driver_code)` (из того же `current_prices`/`RimWorkerSalaryRegistry`, что и для рабочих) к его цене; если ставка нужна, но не нашлась — ресурс честно `unresolved`, не тихая недооценка. `labour_mach == 0` (обычно нет `driver_code` — самоходное/электрическое оборудование без отдельного оператора) — ничего не прибавляется, машина без оператора. `ResourcePriceResolution.machinist_wage_added` — сколько из цены пришлось на эту добавку, для прозрачности перед экспертом. Обратная совместимость: без `machine_labour` (не передан) — поведение как раньше, добавки нет, ни один существующий тест/вызов не сломан. Покрыто юнит-тестами (`test_smeta_estimator_pricing.py`) и вживую на реальных данных Москвы в обоих e2e-тестах.

**Источник подтверждения — устный, не письменный.** На звонке со Smetrix (2026-09-18) практик подтвердил гипотезу Claude про `LabourMach`: это не единая формула на все машины, а свойство конкретной позиции — «для одной техники машинист уже в цене, для другой нет, нужно смотреть по факту записи» (дословно близко к сказанному), что соответствует наблюдаемому паттерну в данных (`LabourMach=1.00` → добавить отдельно, `0` → уже включено/не нужно). **Письменного подтверждения от Smetrix пока нет — ожидается в начале следующей недели.** До этого момента пункт остаётся открытым: если письменный ответ разойдётся с реализованной логикой, `pricing.py`/`fsnb_parser.py`/`models.py` (`MachineLabourInfo`) потребуют пересмотра — это явно помечено в докстрингах всех изменённых мест.

**Независимая проверка по официальным источникам, 2026-09-18 (не решила вопрос до конца, код не менялся):**
- **Исправлена неверная ссылка**: приказ Минстроя №326/пр (05.06.2019), упомянутый раньше как возможный источник методики — это «Методика расчёта ИНДЕКСОВ изменения сметной стоимости строительства», не про формулу оплаты труда машинистов вообще. Реально применимый и действующий документ — приказ №421/пр от 04.08.2020 «Методика определения сметной стоимости строительства...», раздел IV, п.79–83, формула (1.1) — введена/переписана приказом №557/пр от 07.07.2022, актуальность подтверждена: последующие правки (приказ №30/пр от 23.01.2025, приказ №42/пр от 30.01.2026, действует с 14.02.2026) пп.79–82 не затрагивают.
- **Подтверждено официально (несколько независимых источников):** оплата труда машинистов (ОТм) считается ОТДЕЛЬНО от стоимости эксплуатации машины (ЭММ), не входит в неё по умолчанию — формула (1.1) в 421/пр: ОТм = ΣΣ ЗТki×СЦk×Vi, где ЗТki — трудозатраты машиниста по машине k на измеритель сметной нормы (чел.-ч), СЦk — сметная цена его труда в текущем уровне цен (руб./чел.-ч, «на основании данных ФГИС ЦС» — то же значение, что уже подтверждено для рабочих через `RimWorkerSalaryRegistry`). Отдельно приказ №916/пр от 13.12.2021 «Методика определения сметных цен на эксплуатацию машин и механизмов» (в силе, per Минюст №68062, свежее ФСНБ-2022) двумя независимыми пересказами (base.garant.ru, sudact.ru) подтверждает то же самое другими словами: формула цены машино-часа (амортизация+ремонт+топливо+...) оплату труда машиниста не включает, она считается отдельным разделом методики. Отраслевая статья (i-tat.ru) независимо подтверждает: «ФОТ = ОТ + ОТм» — и описывает реальную путаницу у сметных программ с этим на практике, то есть вопрос объективно неочевиден, не только для этого проекта.
- **Всё ещё НЕ подтверждено ни одним источником:** что именно поле `LabourMach` в XML ФГИС ЦС дословно равно ЗТ (трудозатратам машиниста на машино-час) из формулы (1.1) — это остаётся правдоподобной, но не процитированной нигде реконструкцией (по паттерну в данных: `LabourMach=1.00`, когда есть `DriverCode`/`MachinistCategory`, и `0`, когда их нет). Официальных описаний конкретно этого XML/API-поля ФГИС ЦС в открытом доступе не нашлось — попытки достать разъяснения от сметных программ (ГРАНД-Смета, Турбосметчик), которые по идее должны были решить эту же задачу для тех же данных ФГИС ЦС, не удались технически (страницы на JS, не отдают текст без браузера).
- **Отдельно подтверждено вживую, 2026-09-18: «машинист» — единый обобщающий термин, отдельной категории «водитель» в данных нет.** Живой запрос `fetch_worker_salary_registry()` за Москву (не фикстура — реальные 186 позиций реестра на 3 квартал 2026) показал, что все 91 позиции с кодом `4-100-XXX` названы дословно одинаково — `"Средний разряд машинистов"` + номер разряда, различаются только разрядом (1,0–10,0+), не видом техники и не профессией. Слова «водитель» нет ни в одной из 186 записей реестра вообще. Это подтверждает, что `DriverCode` в ФСБЦ_Маш.xml (английское название поля, само по себе двусмысленное) для любой техники — включая грузовой автомобиль `91.14.02-001 "Автомобили бортовые"`, которым в быту скорее управляет «водитель» — указывает именно в общий пул «машинистов» по разряду, а не в отдельную категорию водителей. Другие категории того же реестра для контраста: `1-100`/`2-100` — рабочие, `3-100..3-400` — техники/инженеры, `5-100` — исполнители реставрационных работ.
- **Новый вопрос, всплывший в ходе проверки, не было в CLAUDE.md раньше:** та же неопределённость может касаться не только пути «базовая цена × индекс ГОСР», но и пути «текущая цена напрямую» (`current_prices`, приоритет 1 в `pricing.py`) — включает ли `estimatedPrice` из `/BuildingResources/Search/Machines` оплату труда машиниста уже внутри, или тоже нужно доплюсовывать `LabourMach × ставка`. Не проверено ни в одну сторону.

Стоит спросить его отдельно и про `LabourMach`, и про то, включает ли `estimatedPrice` зарплату машиниста; также у Edwin может быть доступ к разделу «База знаний» ФГИС ЦС (`fgiscs.minstroyrf.ru/#/Knowledges`) с более точным описанием полей API, если найдётся время проверить напрямую.
13. **Часть материалов ГЭСН задана категорией, не конкретным продуктом** (`<AbstractResource>` в XML, `abstract_resource_codes` в `GesnWorkItem`) — например «Материалы рулонные кровельные для нижних слоев» без указания, что конкретно использовать. Это не пробел в данных, который можно закрыть поиском источника — **это продуктовое решение владельца**: автоматически подставлять какой-то конкретный продукт категории (самый дешёвый? самый популярный по объёму продаж?) или оставлять выбор эксперту в каждом случае вручную. Пока не решено — остаётся `unresolved`, эксперт видит категорию и выбирает сам.
14. **Покрытие ГОСР по машинам неполное — закрыто комбинированием с текущими ценами, 2026-09-18 вечером.** На реальном примере (Москва, 3 квартал 2026) из 5 машинных кодов тестовой позиции индекс ГОСР нашёлся только для 2 — но проверка показала, что для остальных 3 в этот же квартал была опубликована текущая цена напрямую (`/BuildingResources/Search/Machines`). Вместе источники покрыли все 5 — не совпадение, а ожидаемая логика: ФГИС ЦС публикует для ресурса либо текущую цену, либо ГОСР-индекс, редко оба сразу. Остаточный риск: для реального полного каталога (30 028 позиций) не проверено, есть ли коды без обоих источников сразу — они по-прежнему честно останутся `unresolved`, не тихим нулём, если такое случится.
15. **Пагинация API текущих цен — проверена и защищена, 2026-09-18 вечером, не просто отмечена как риск.** Подтверждено вживую: у `RimWorkerSalaryRegistry` `take` реально ограничивает выдачу (Москва: `total=186`, `take=100` вернул только 100 — без догрузки часть ставок терялась бы молча); `fetch_worker_salary_registry` теперь честно догружает страницы до `total`. У `BuildingResources/Search/*` на практике `take` не ограничивал выдачу (Москва: ~2700 материалов пришли одним ответом), но `fetch_current_prices_json` всё равно не доверяет этому слепо — сверяет фактическое количество с `total` и повторяет запрос с большим `take`, если не сошлось, вместо того чтобы тихо вернуть неполные данные. Поиск по коду ресурса через параметр `search=` не сработал при проверке (пустой результат) — используется полная выгрузка категории с локальным поиском по коду, не серверная фильтрация (не проблема после исправления пагинации, просто иначе устроено, чем ожидалось).
16. **`DEFAULT_ARCHIVE_URL` (`fsnb_client.py`) и `CURRENT_PERIOD_ID` (`regional_pricing_client.py`) — захардкожены на конкретную версию/квартал, не отслеживаются автоматически.** Перепроверено 2026-09-18 вечером — 3 квартал 2026 всё ещё актуален, новых версий не появилось. Осознанно не стал делать автообновление сейчас (это отдельная инженерная задача — завести то же отслеживание версий через Агента 10, что уже есть для самих индексов ГОСР, — не вопрос недостающей информации), обновлять вручную по мере выхода новых версий.
17. **Агент 4 подключён к Агенту 5 (`src/smeta_estimator/cost_estimate.py`, 2026-09-18), но объём работ по смете конкретной закупки — не автоматизированный внешний вход, а ручной параметр (`SmetaLineItem.work_volume`).** Это единственное место в этой связке, где стык получился не таким гладким, как между Агентом 3 и Агентом 6: там Агент 3 сам извлекает из текста документации всё, что нужно Агенту 6. Здесь же ни Агент 3 (извлекает сроки/обеспечение/риски, не ведомость объёмов работ), ни Агент 4 (не реализовано — см. таблицу ниже) не считают, сколько именно "100 м2" кровли или "м3" бетона нужно по конкретной закупке — эту цифру по-прежнему подставляет человек. `build_cost_estimate()` требует `MatchResult.expert_reviewed=True` для каждой позиции (тот же гейт, что у Агента 3 в `assemble_document_package()`/`estimate_profitability()`) и передаёт себестоимость в `CostEstimate` с новыми полями `expert_reviewed`/`is_complete` — `estimate_profitability()` отказывает, если `expert_reviewed=False`, и добавляет риск-флаг, если `is_complete=False` (часть позиций сметы не оценена или оценена частично), не блокируя расчёт маржи целиком.
18. **Переходник Агент 1 -> Агент 2 (`eis_client.tender_adapter.document_to_tender()`, 2026-09-21) закрывает совместимость типов, но не сам источник данных.** `_find_reestr_number()` (`client.py`) — та же tag-name-эвристика, что уже была у ОКПД2-поиска (`_find_okpd2_codes`), и с тем же уровнем доверия: **не подтверждена на реальных документах ЕИС**, потому что сервис до сих пор отвечает эхом запроса, а не реальными архивами (см. п.3) — просто обоснованное предположение по одному примеру `<reestrNumber>` из общедоступной инструкции (`docs/eis-integration-instruction-2025.pdf`), явно отличённое от `regNum` организации (другое поле, другой смысл, в том же примере). Остальные 8 полей `Tender` (`name`, `customer_name`, `region_code`, `max_price`, `requires_sro`, `min_experience_years`, `publish_date`, `submission_deadline`) переходник принципиально не извлекает сам — их схема в закрытом Альбоме ТФФ ЕИС (см. п.4), поэтому `document_to_tender()` требует их явными обязательными keyword-параметрами и отказывает (`TypeError`/`ValueError`), если чего-то не передали, вместо заглушки. Как только появятся реальные документы (когда п.3 разрешится) — первым делом нужно проверить: (а) действительно ли `_find_reestr_number` находит правильное значение на реальных данных, (б) видны ли в реальном документе тег-кандидаты хотя бы для части оставшихся 8 полей той же эвристикой.

Отдельно — черновик более формальной формулировки для будущего договора-оферты (`docs/legal-boundary-draft.md`). Оба текста не проверены юристом (см. «Известные пробелы», п.8) |

## Интерфейс эксперта-проверяющего

- `src/review_queue.py` — интерактивный CLI (не сайт): показывает всё, что ждёт решения Edwin, и даёт ответить да/нет прямо в терминале, не трогая код.
  - Реальная очередь: все записи `PENDING` у Агента 10 (`RegulatoryUpdateStore.list_pending()`) — с diff по пунктам и настоящим `approve_update()`/отклонением с причиной.
  - Учебный пример по источнику документов, но не по обработке решения: три тестовых документа Агента 3 (`sample_documents.py`), прогнанные через `extract_requirements()` при каждом запуске. Само решение эксперта, однако, реально прогоняется через `document_analyst.review_document_analysis()` (`AuditReadinessTracker`/`CategorizedDiscrepancyLog`, 2026-09-21) — не только помечает объект в памяти. Не сохраняется только сама метрика между запусками CLI (у Агента 3 нет постоянного хранилища результатов, см. «Известные пробелы»).
- **Заметка на будущее, не сейчас:** терминал годится, пока проверяющий — один человек (Edwin) и очередь короткая. Если объём вырастет или проверяющих станет больше, для реального интерфейса может понадобиться что-то удобнее — веб-страница в самом продукте или общая Google-таблица с формулами/фильтрами. Явного решения пока нет, `review_queue.py` — временное практичное решение под текущий масштаб пилота.

## Протокол контроля качества — обязательные правила, без исключений

- Выдача агентов 3, 4, 6 (документация, смета, пакет документов) не уходит клиенту без подтверждения эксперта-человека, пока не накоплена статистика и не согласован переход на выборочный аудит.
- Профиль клиента (агент 11) проверяется на полноту и достоверность до того, как им пользуется агент 6.
- Любое обновление нормативной базы (агент 10) применяется только после подтверждения эксперта — автоматическое применение запрещено.
- **Автоматическая подача заявки и автоматическая подпись КЭП без участия собственника — исключены архитектурно.** Не реализовывать эту функциональность ни в каком виде, даже как опцию.
- Если агент выдаёт смету/документацию — обязательно указывать дату актуальности нормативных данных, на которые опирается расчёт.

## Технические решения, уже принятые

- Продукт: сайт (веб-приложение) + Telegram-бот. Нативные iOS/Android — не на старте.
- Источник данных ЕИС: официальный доступ через zakupki.gov.ru, регистрация как «физическое лицо, индивидуальный предприниматель» → токен (не mTLS-сертификат, это только для юрлиц). Переменная `EIS_CONSUMER_TYPE=individual_person`. Не FTP, не HTML-скрапинг — ненадёжно и неполно по НМЦК; открытый FTP ЕИС закрыт с 01.01.2025.
- Метрика готовности агента к переходу с полной проверки эксперта на выборочный аудит (применяется к агентам 3, 4, 6): скользящее окно 50 проверок, ≥90% без существенной корректировки, 0 критических ошибок, откат при любой критической ошибке после перехода.
- Хостинг для постоянно работающих агентов (монитор и далее) — Railway, отдельный новый проект на существующем аккаунте Edwin, не смешивать с другими его проектами.
- Агент 10 (Парсер нормативки, `src/regulatory_updates`): подтверждение экспертом обязательно для абсолютно каждой версии источника, включая самую первую («нулевую», когда предшественника ещё нет) — осознанное решение владельца, не временная заглушка. **Заметка на будущее, не сейчас:** если на практике подтверждать по одной 10-15 региональных версий вручную окажется неудобно, можно добавить пакетное подтверждение (одобрить сразу несколько `PENDING`-записей одним действием) — это только ускорение самого процесса подтверждения, саму обязательность экспертной проверки такая доработка не отменяет.
- Налоговый режим в профиле клиента (Агент 11, `onboarding.tax_config`): вместо свободного текста «система налогообложения» + отдельного дохода, из которых сервису пришлось бы самому вычислять ставку НДС и следить за порогами/индексацией УСН — клиент выбирает готовую комбинацию режим+ставка сам, из ровно 8 фиксированных вариантов (`TaxRegimeChoice`: УСН 6%/15% без НДС или с НДС 5%/7%, ОСН+НДС 22%, либо «другое — уточнить с бухгалтером»). Агент 5 (когда будет спроектирован) берёт ставку прямо из этого выбора, не вычисляет её. `tax_config.py` — справочник для валидации выбора в форме, не калькулятор; там же `UNVERIFIED_NOTES` с непроверенной информацией о возможном возврате ставки НДС к 20% с 2027 года — заметка на будущее, автоматически ничего не меняет. Среднегодовая выручка (`avg_annual_revenue`) осталась отдельным полем для другой цели — финансовой состоятельности клиента у Агента 2, с налоговым режимом не связана.

## Стиль работы

- Объяснять технические шаги простыми словами — владелец не разработчик.
- Не делать необратимых или дорогостоящих шагов (деплой в прод, трата денег на подписки/API) без явного подтверждения.
- Каждое техническое решение сверять с протоколом контроля качества выше.
- Коммитить и пушить в GitHub после каждого законченного куска работы, не ждать полной готовности всего агента.
